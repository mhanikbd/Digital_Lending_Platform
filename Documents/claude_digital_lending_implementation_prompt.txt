You are implementing a production-grade, configurable Digital Lending Platform for local Bangladeshi banks.

# 1. PROJECT OBJECTIVE

Build a bank-grade Digital Lending & Account Opening Platform supporting:

1. Customer Mobile App — Flutter
2. Field Officer Mobile App — Flutter
3. Bank Back-office Web Application — Next.js + TypeScript
4. Backend — Java 21 + Spring Boot
5. Primary Database — PostgreSQL
6. Cache / short-lived state — Redis
7. Document/Object Storage — MinIO / S3-compatible storage
8. Future event platform — Kafka
9. Infrastructure — Docker, Nginx/API Gateway, Prometheus, Grafana, Loki

The first complete lending product must be e-Loan. The architecture must then allow Quick Loan, Instant Loan, Personal Loan, Car Loan, Student Loan, Home Loan, SME/CMSME Loan and Credit Card products to be introduced primarily through configuration rather than separate codebases and workflows.

The platform must support both digital customer-originated applications and Field Officer-assisted applications.

It must also support the separate New Customer Account Opening journey and the bank-side account-opening approval workflow.

# 2. NON-NEGOTIABLE ARCHITECTURE PRINCIPLES

## 2.1 Backend owns authoritative business logic

Flutter and Next.js are client/presentation layers.

They must NOT contain authoritative logic for:

- Loan eligibility
- Loan limits
- Interest calculation
- EMI calculation
- Fees
- Approval authority
- Workflow transitions
- Credit decisions
- DPD
- NPL classification
- Repayment allocation
- Regulatory limits

All authoritative decisions must be made by Spring Boot.

The mobile/web clients should request decisions from APIs.

## 2.2 Configuration over hard-coding

The following must be configurable from the Admin Portal:

- Loan products
- Product versions
- Product parameters
- Eligibility criteria
- Eligibility rule groups
- Credit rules
- Loan amount limits
- Tenure
- Interest/profit
- Fees
- VAT
- Insurance
- Repayment frequency
- Grace period
- Required documents
- Customer eligibility
- Risk rules
- DBR rules
- Approval limits
- Approval hierarchy
- Workflow states
- Workflow transitions
- NPL/DPD rules
- Notification rules
- Regulatory parameters

Do not hard-code product-specific business rules in Java services.

## 2.3 Product versioning

Every loan product must be versioned.

Example:

eLoan
- Version 1
- Version 2
- Version 3

Applications must store:

- product_id
- product_version_id

Old applications and loans must continue to use the configuration under which they were evaluated/approved.

Never modify live product rules in-place without creating a new version.

## 2.4 Financial precision

Never use float or double for monetary calculations.

Use:

- PostgreSQL NUMERIC
- Java BigDecimal

Recommended financial precision:

NUMERIC(20,4)

## 2.5 Modular monolith first

Do NOT start with microservices.

Build one Spring Boot modular monolith with clearly separated domain modules.

Possible future extraction into microservices may happen only after scale requirements justify it.

## 2.6 Database authority

PostgreSQL is authoritative for:

- Customer
- KYC
- Account application
- Loan application
- Loan
- Workflow state
- Approval
- Repayment
- Balance
- Collection
- NPL
- Audit
- Document metadata

## 2.7 Database migrations

Use Flyway.

Never make undocumented schema changes.

Every schema modification must have a Flyway migration.

## 2.8 API design

Use REST APIs with versioning:

/api/v1/...

Use DTOs. Never expose JPA entities directly from controllers.

Every API should have:

- Request validation
- Authorization
- Consistent response structure
- Error handling
- Logging
- Correlation ID
- OpenAPI documentation

# 58. CLAUDE WORKING METHOD

Do NOT attempt to implement the entire system in one operation.

For every milestone:

1. Inspect the repository.
2. Review existing implementation.
3. Identify dependencies.
4. State the intended implementation plan.
5. Implement database migrations.
6. Implement backend.
7. Implement tests.
8. Run tests.
9. Fix failures.
10. Implement frontend.
11. Run frontend tests/build.
12. Update documentation.
13. Provide a concise implementation report.
14. Stop and wait before beginning the next major milestone unless explicitly instructed to continue.

Do not overwrite working code unnecessarily.

Do not introduce dependencies without justification.

Do not create speculative abstractions.

Do not create speculative database tables.

Prefer simple, maintainable, production-grade implementations.
